# 01. Как это работает

## Устройство

```
                        события mpv (observe_property)
   mpv ═══════════════════════════════════════════▶ Tracker (src/tracker.rs)
    ▲                                                │  значения свойств → снимок
    │                                                │  Recorder: «не затирать пустым»
    │                                                ├──▶ SharedState.last  (память)
    │                                                └──▶ state.json        (если файл писабелен)
    │  get_property по запросу
    └──────────── Sampler (src/sampler.rs) ◀── `get`  ┐
                                                      ├── клиенты сокета (src/output/socket.rs)
                  SharedState (src/shared.rs) ◀── `last`, `status` ┘
```

У наблюдателя два соединения с mpv, у каждого своя задача:

- **трекер** подписывается на нужные свойства (`observe_property`) и дальше
  только слушает события. mpv сам сообщает о каждом изменении, поэтому
  опроса по таймеру нет;
- **sampler** нужен только для `get`: он заново читает все свойства в момент
  запроса.

## Трекер (`src/tracker.rs`)

1. Подключается, читает `pid` и `mpv-version`, подписывается на 13 свойств из
   `SNAPSHOT_PROPERTIES`. В ответ на подписку mpv сразу присылает текущее
   значение, так что начальное состояние известно без отдельного опроса.
2. Каждое событие `property-change` кладёт новое значение в словарь
   `PropertyValues` и **планирует** снимок:
   - через 200 мс для обычных свойств — mpv присылает их пачкой (при
     подключении, при старте файла), и снимок делается, когда пачка кончилась;
   - через 1 с для `time-pos` — позиция меняется много раз в секунду, а для
     восстановления хватит секундной точности.

   Уже запланированный более ранний снимок не откладывается.
3. Снимок (`PlayerSnapshot::from_properties`) проходит через `Recorder`
   (правило ниже) и, если изменился, становится `last` в `SharedState`.
4. Затем решается, писать ли файл (если он писабелен):
   - изменилось что-то кроме позиции (файл, плейлист, пауза, громкость,
     дорожки) или сменился pid — сразу;
   - пришло событие `playback-restart` (после перемотки) — сразу;
   - изменилась только позиция — не чаще `position-save-seconds`;
   - при остановке наблюдателя (SIGTERM при перезагрузке) — финальная запись,
     если в памяти есть что-то незаписанное.
5. Связь с mpv пропала — снимок остаётся, раз в секунду попытка
   переподключиться.

`select!` в цикле ждёт одного из трёх событий: строку от mpv, срок
запланированного снимка, сигнал остановки. `next_event` безопасна при отмене:
единственная точка ожидания внутри — `next_line`, так что событие не
потеряется.

## Правило «не затирать снимок» (`src/recorder.rs`)

| Предыдущий снимок | Новый снимок | Решение |
|---|---|---|
| нет | любой | `Publish` |
| pid A, что-то играло | pid B, плейлист пуст | `HoldPrevious` |
| pid A | pid A, то же самое | `Unchanged` |
| pid A | pid A, изменилось (позиция, громкость, стоп) | `Publish` |
| pid A | pid B, что-то играет (восстановили или запустили новое) | `Publish` |

`Recorder` — чистая логика без ввода-вывода, все строки таблицы проверены
тестами.

## Файл состояния и режим «только для чтения»

При старте `probe_state_file` проверяет каталог файла по-честному: создаёт и
удаляет пробный файл. Проверять права по битам бессмысленно: всё решают
монтирование, ACL и владелец.

| Режим | Когда | Поведение |
|---|---|---|
| `read-write` | запись удалась | старый файл загружается и продолжает вестись |
| `read-write`, `volatile` | каталог на tmpfs/overlay | то же, плюс предупреждение: файл в RAM, после выключения пропадёт |
| `read-only` | запись не удалась | файл **не читается и не пишется**: старый файл в неписабельном месте мог остаться от чего угодно (например, лежать в образе карты) |
| `not-configured` | `state-file` закомментирован | снимок только в памяти |

Без писабельного файла `last` после перезапуска наблюдателя отвечает
`"known": false`. Это и есть «плеер не запущен, состояние неизвестно», и
REST-сервис тогда ничего не восстанавливает.

Писабельность проверяется один раз при старте. Если раздел станет
read-only во время работы (ядро так делает при ошибках ФС), запись просто
перестанет удаваться: ошибка будет в логе и в `status`
(`last-write-error`), а снимок в памяти продолжит обновляться.

Атомарная запись (временный файл → `fsync` → `rename`) гарантирует, что
выдёргивание из розетки оставит либо старый файл, либо новый. `fsync` идёт в
`spawn_blocking`, чтобы не блокировать единственный поток.

## Сокет (`src/output/socket.rs`)

По задаче на клиента. Каждая строка запроса получает одну строку ответа:

- `get` → `Sampler::capture_live`: свежий опрос mpv, или
  `"mpv-reachable": false` с причиной;
- `last` → копия `SharedState.last`, или `"known": false`;
- `status` → состояние соединения с mpv, режим файла, последняя запись.

Старый файл сокета после аварийного завершения удаляется при старте, но только
если это действительно сокет.

## systemd

- `Type=notify` + `READY=1`, `WatchdogSec=60` + `WATCHDOG=1` из главного цикла
  с половинным периодом.
- `StateDirectory=` убран: на read-only корне systemd не смог бы его создать,
  и юнит не запустился бы. Писать разрешено только в
  `ReadWritePaths=-/srv/remoteplayer/state/mpvwatcher`; минус означает «если
  каталога нет — не страшно».
- `RuntimeDirectory=` (сокет) остаётся: `/run` — это tmpfs, он писабелен
  всегда.
- При остановке главный цикл сигналит трекеру через `watch`-канал и даёт ему
  до 5 секунд на финальную запись.
