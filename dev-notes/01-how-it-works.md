# 01. Как это работает

## Два независимых выхода, один источник

```
                    ┌──────────── Sampler (src/sampler.rs) ────────────┐
 таймер файла ─────▶│ capture_reusing(interval)                        │
 (если state-file)  │   свежий снимок моложе интервала? → вернуть его  │──▶ сокет mpv
                    │   иначе → опросить mpv                           │    (одно соединение)
 клиент сокета ────▶│ capture_live() → всегда опросить mpv             │
 (`get`)            │ последний снимок запоминается                    │
                    └──────────────────────────────────────────────────┘
 таймер файла → Recorder → state.json          клиент сокета → одна строка JSON в ответ
```

- **Файл** включается строкой `state-file`. Каждые
  `state-file-interval-seconds` таймер просит у `Sampler` снимок. Если клиент
  сокета уже спрашивал mpv в пределах интервала, повторного опроса нет: берётся
  тот результат. Дальше `Recorder` решает, писать ли файл (см. ниже).
  Закомментировал `state-file` — нет ни таймера, ни периодических опросов.
- **Сокет** включается строкой `state-socket`. Сам он ничего не шлёт. На `get`
  mpv опрашивается сразу, и ответом приходит одна строка. Частоту задаёт клиент:
  REST-сервис или кто угодно ещё.
- `Sampler` — единственный, кто разговаривает с mpv. Соединение одно, оно
  лежит под асинхронным мьютексом, поэтому опрос от таймера и опрос по `get`
  не перемешаются в одном соединении: второй дождётся конца первого.

Опрос — это около 15 запросов `get_property` подряд по одному соединению.
Если mpv перезапустился, первый же запрос получит ошибку, соединение
сбросится, а следующий опрос установит новое. В лог попадают только переходы
«подключён ↔ не подключён».

## Правило «не затирать снимок» — только для файла (`src/recorder.rs`)

Зачем вообще нужен наблюдатель: mpv падает, systemd через 3 секунды поднимает
новый — пустой. Если бы файл просто повторял то, что видно сейчас, через один
интервал в нём было бы «ничего не играет», и восстанавливать было бы нечего.

| Предыдущий снимок в файле | Новый снимок | Решение |
|---|---|---|
| нет | любой | `Publish` |
| pid A, что-то играло | pid B, плейлист пуст | `HoldPrevious` |
| pid A | pid A, то же самое | `Unchanged` (ничего не пишем) |
| pid A | pid A, изменилось (позиция, громкость, стоп) | `Publish` |
| pid A | pid B, что-то играет (восстановили или запустили новое) | `Publish` |

Предыдущий снимок при старте читается из файла, поэтому правило работает и
после перезагрузки Pi.

Ответ на `get` этого правила не знает: он показывает mpv как есть, и сразу
после падения это будет пустой новый mpv. Поэтому REST-сервис
восстанавливается после падения именно по файлу. Без `state-file` — значит,
без автоматического восстановления.

`Recorder` — чистая логика без ввода-вывода, все строки таблицы проверены
юнит-тестами.

## Выходы

**Файл** (`src/output/file.rs`): временный файл рядом → `write` → `fsync` →
`rename`. Читатель, nginx или отключение питания видят либо старый файл,
либо новый — половины файла не бывает. `fsync` на SD-карте может занять
заметное время, поэтому он выполняется в `spawn_blocking`, а не в
единственном потоке, который отвечает клиентам сокета.

**Сокет** (`src/output/socket.rs`): `UnixListener` и по задаче на каждого
клиента. Задача читает строки и на каждую отвечает одной строкой: `get` →
состояние, пустая строка — пропуск, всё остальное — `{"error": ...}`.
Соединение можно держать открытым и спрашивать сколько угодно раз. Старый
файл сокета, оставшийся после аварийного завершения, удаляется при старте,
но только если это действительно сокет: ошибка в конфигурации не удалит
обычный файл (есть тест).

## Главный цикл (`src/main.rs`)

`select!` ждёт одного из четырёх событий: тик таймера файла, тик сторожевого
таймера systemd, Ctrl+C, SIGTERM. Если таймер не нужен (нет `state-file`,
нет watchdog), вместо него стоит future, которая не завершается никогда
(`std::future::pending`), — и этот вариант просто никогда не выигрывает.

## systemd

- `Type=notify` + `READY=1` после старта: systemd считает сервис запущенным,
  когда он действительно готов.
- `WatchdogSec=60`: systemd передаёт период в переменной `WATCHDOG_USEC`, и
  наблюдатель шлёт `WATCHDOG=1` вдвое чаще — это рекомендованный запас. Пинг
  идёт из главного цикла, так что зависший цикл systemd перезапустит.
  Пинги не зависят от `state-file`: watchdog работает и в режиме «только
  сокет».
- `RuntimeDirectory=` / `StateDirectory=` создают `/run/...` и `/var/lib/...`
  с владельцем `coop`; `UMask=0077` делает файл и сокет доступными только
  этому пользователю — тем же процессам, что видят сокет mpv. Если файл
  должен отдавать nginx, ему понадобится доступ к каталогу: например, общая
  группа и `UMask=0027` с `StateDirectoryMode=0750`.
- Песочница: `ProtectSystem=strict`, `PrivateDevices=yes`,
  `RestrictAddressFamilies=AF_UNIX`. Наблюдателю не нужны ни сеть, ни
  устройства.
