# 01. Как это работает

## Цикл

```
каждые interval-seconds (7 с):
    нет соединения с mpv?  → подключиться, отправить `disable_event all`
    снять Capture (≈15 запросов get_property по одному)
        ошибка ввода-вывода/таймаут → бросить соединение, ждать следующего тика
    Recorder::consider(capture) → Publish | Unchanged | HoldPrevious
    Publish → строка в сокет + атомарная запись файла (в spawn_blocking)
    sd_notify WATCHDOG=1
```

- Таймер `tokio::time::interval` с `MissedTickBehavior::Delay`: если Pi был
  занят и тик пропущен, пропущенные тики не «догоняются» пачкой, а следующий
  идёт через полный интервал.
- Соединение одно и живёт между тиками. Если mpv перезапустился, первый же
  запрос получит ошибку записи или EOF, соединение сбросится, а на следующем
  тике установится новое.
- В лог попадают только переходы «подключён ↔ не подключён», а не каждая
  неудачная попытка раз в 7 секунд.

## Правило «не затирать снимок» (`src/recorder.rs`)

Зачем вообще нужен наблюдатель: mpv падает, systemd через 3 секунды
поднимает новый — пустой. Если бы наблюдатель просто записывал то, что
видит, через 7 секунд в файле было бы «ничего не играет», и восстанавливать
стало бы нечего.

| Предыдущий снимок | Новый снимок | Решение |
|---|---|---|
| нет | любой | `Publish` |
| pid A, что-то играло | pid B, плейлист пуст | `HoldPrevious` |
| pid A | pid A, то же самое | `Unchanged` (ничего не пишем) |
| pid A | pid A, изменилось (позиция, громкость, стоп) | `Publish` |
| pid A | pid B, что-то играет (восстановили или запустили новое) | `Publish` |

Предыдущий снимок при старте читается из файла, поэтому правило работает и
после перезагрузки Pi: новый mpv с новым pid и пустым плейлистом файл не
затрёт. Как только REST-сервис восстановит воспроизведение (или пользователь
запустит что-то своё), наблюдатель начнёт писать состояние нового процесса.

`Recorder` — чистая логика без ввода-вывода, поэтому все строки этой таблицы
проверены юнит-тестами.

## Выходы

**Файл** (`src/output/file.rs`): временный файл рядом → `write` → `fsync` →
`rename`. Читатель или отключение питания видят либо старый файл, либо
новый — половины файла не бывает никогда. `fsync` на SD-карте может занять
заметное время, поэтому он выполняется в `spawn_blocking`, а не в
единственном потоке, который обслуживает клиентов сокета.

**Сокет** (`src/output/socket.rs`): `UnixListener` и по задаче на клиента.
Последняя строка хранится в `tokio::sync::watch`. Это канал, который помнит
одно последнее значение и будит подписчиков при изменении. Новый клиент сразу
получает текущее состояние, затем каждое изменение; на строку `get` отвечает
повторно. Старый файл сокета, оставшийся после аварийного завершения,
удаляется при старте, но только если это действительно сокет. Ошибка в
конфигурации не удалит обычный файл (есть тест).

## systemd

- `Type=notify` + `READY=1` после старта: systemd считает сервис запущенным,
  когда он действительно готов.
- `WatchdogSec=60` + `WATCHDOG=1` после каждого тика: если цикл зависнет,
  systemd перезапустит наблюдатель.
- `RuntimeDirectory=` / `StateDirectory=` создают `/run/...` и `/var/lib/...`
  с владельцем `coop`; `UMask=0077` делает файл и сокет доступными только
  этому пользователю, то есть тем же процессам, что видят сокет mpv.
- Песочница: `ProtectSystem=strict`, `PrivateDevices=yes`,
  `RestrictAddressFamilies=AF_UNIX`. Наблюдателю не нужны ни сеть, ни
  устройства.
